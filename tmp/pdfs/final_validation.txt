          API-01         OTP delivery channel and fallback

         Priority                  P0 - blocks WhatsApp-first OTP

         Affected                  POST /auth/signin-with-otp; POST /auth/sign-up-with-otp; POST /auth/resend-otp; POST
         endpoints                 /auth/verify-otp

         Current gap               The app can request and verify OTP, but the response does not expose which transport was used or
                                   whether WhatsApp failed over to SMS.

         Required change           Accept deliveryChannel (email, whatsapp, sms) and fallbackChannel. For phone OTP, attempt
                                   WhatsApp first and fall back server-side to SMS. Return deliveryChannelUsed, fallbackAttempted,
                                   maskedIdentifier, otpLength, and retryAfterSeconds.

         Acceptance                A phone request produces one logical OTP transaction; verification uses the same transaction
         criteria                  regardless of transport; resend respects a server-supplied 30-second retry window.

          API-02         Onboarding profile fields and persistence

         Priority                P0 - blocks three requested onboarding sections

         Affected                POST /users/onboarding; GET /users/profile; relevant PUT /users/profile/* endpoints
         endpoints

         Current gap             The current SignUpRequestBody has no religious-practice, two marriage-intention, institute,
                                 additional-institute, or hide-income fields.

         Required change         Add religiousPractice; connectionTimeline; marriageTimeline; institute; additionalInstitute; hideIncome.
                                 Recommended enum values: very_religious, moderately_religious, somewhat_religious,
                                 not_very_religious, prefer_not_to_say; 1_3_months, 3_6_months, 6_12_months, 1_2_years;
                                 within_6_months, 6_12_months, 1_2_years, 2_3_years, no_rush, decide_together.

         Acceptance              Create, read, and update return the same canonical values; optional fields may be omitted; Open To All
         criteria                religion permits religiousPractice to be null.



          API-03         Authoritative lookup and location datasets

         Priority                P1 - blocks exact dropdown parity

         Affected                GET /lookups; GET /countries; GET /cities
         endpoints

         Current gap             The client report requires exact religion, education, work-sector, profession, income, country, and city
                                 datasets. Current client fallbacks and returned datasets are not guaranteed to match.

         Required change         Publish versioned categories for religions, education_levels, work_sectors, professions,
                                 income_ranges, and mother_tongues. Country/city responses should include stable id, code, label,
                                 sortOrder, isActive, and isTopCity. Cities must support country, search, page, and size.

         Acceptance              Bangladesh resolves all 64 districts; required country counts are available; mobile clients render labels
         criteria                but submit stable keys; removed keys remain backwards compatible during migration.



          API-04         Ten-category interests taxonomy

         Priority                P1 - blocks full hobbies requirement

         Affected                GET /lookups?category=interests (or GET /interests/taxonomy); PUT /users/profile/interests
         endpoints

         Current gap             The existing update body uses six fixed arrays and cannot represent all ten client categories reliably.

         Required change         Return category objects with id, key, label, sortOrder, minimumSelection, and items. Accept
                                 selectedInterestIds as a flat stable-id array, or accept categories [{categoryKey, itemKeys}]. Keep the
                                 old six arrays during a deprecation window.

         Acceptance              At least 86 active items can be returned; the server validates a minimum of five unique selections; GET
         criteria                returns the selected IDs after PUT.

          API-05         Family status and financial enum alignment

         Priority                P1 - blocks family/financial parity

         Affected                PUT /users/profile/family; GET /users/profile/family
         endpoints

         Current gap             The current model has fatherProfession and motherProfession but no parent-status fields. Existing
                                 familyEconomicCondition values do not match the four client choices.

         Required change         Add fatherStatus and motherStatus. Support employed, self_employed_business, retired,
                                 not_employed, homemaker (mother), deceased, prefer_not_to_say. Align financialStatus to wealthy,
                                 upper_middle_class, middle_class, prefer_not_to_say, or publish a documented mapping from the
                                 legacy field.

         Acceptance              All fields are optional; sibling counts accept 0-10; read-after-write preserves Prefer not to say without
         criteria                converting it to null.



          API-06         Partner-preference filtering semantics

         Priority                P1 - blocks exact preference behavior

         Affected                PUT/GET /users/profile/preferences; GET /matches
         endpoints

         Current gap             Open To All is ambiguous across marital status, religion, mother tongue, location, education, profession,
                                 and income. Community is still supported although the client report removes it.

         Required change         Define Open To All as an omitted/empty filter or accept a canonical open_to_all key consistently.
                                 Document whether mixed selections containing open_to_all are rejected or normalized. Confirm
                                 whether communityPreference is deprecated. Accept stable lookup keys in all arrays.

         Acceptance              Saved preferences and match-query behavior are identical; Open To All never accidentally filters out
         criteria                profiles; deprecated community data remains readable during migration.



          API-07         Suggested-match verification and photo entitlements

         Priority                P1 - blocks exact badge/blur rules

         Affected                GET /matches; POST /connections/bulk-send
         endpoints

         Current gap             The match response has nested photo visibility and photo verification data, but no unambiguous
                                 profile-level verified badge or explicit can-view-photo entitlement.

         Required change         Return profileVerified (or verificationStatus), profilePhoto.canView, profilePhoto.blurRequired, and
                                 profilePhoto.blurReason. Keep visibilityStatus for compatibility. Bulk-send should return per-user
                                 success/failure and ignore already-connected profiles idempotently.

         Acceptance              The client never infers verification from premium status; clear versus blurred photos are decided by
         criteria                response flags; all preselected eligible IDs can be submitted safely.

          API-08         Premium plan content and entitlement contract

         Priority                P2 - makes premium screen authoritative

         Affected                GET /plans; GET /payments/subscription; POST /payments/initiate
         endpoints

         Current gap             Plan prices are dynamic, but the client report also specifies guarantee days and exact feature limits.

run end-to-end contract tests.
